Architecture Overview

Vertical Slice Architecture

Each feature is a self-contained vertical slice through all layers

Instead of organizing code by technical layer (Controllers → Services → Repositories), this solution organizes by feature. Each slice owns its command/query, handler, and validator — nothing leaks across slice boundaries.

HTTP Request→ Program.cs→ Feature Handler→ Supplier Entity→ WriteDbContext

Features / Supplier / v1

Versioned feature folder — all Supplier operations live here

CreateSupplier/

Contains CreateSupplierCommand.cs (the input DTO / MediatR command), CreateSupplierHandler.cs (business logic, writes to DB), and CreateSupplierValidator.cs (FluentValidation rules).

Contains GetAllSupplierQuery.cs (the MediatR query, often empty or with filter params) and GetAllSupplierHandler.cs (reads all suppliers from DB and returns a list).

UpdateSupplier/

Contains UpdateSupplierCommand.cs (carries the updated fields + supplier ID), UpdateSupplierHandler.cs (fetches entity, applies changes, saves), and UpdateSupplierValidator.cs.

⭐

Shared / Supplier.cs — Domain Entity

The core domain entity shared across all three slices. Defines the Supplier class with its properties (Id, Name, Email, Phone, CreatedAt). Versioned with v1 so a future v2 can introduce breaking changes without touching this.

📄

Shared / SupplierConfiguration.cs — EF Core Mapping

Implements IEntityTypeConfiguration<Supplier>. Tells EF Core how the Supplier entity maps to the database — table name, column types, constraints, indexes. Lives next to Supplier.cs because it has no reason to exist without it. In pure VSA the slice owns its persistence mapping.

public class SupplierConfiguration
    : IEntityTypeConfiguration<Supplier>
{
    public void Configure(EntityTypeBuilder<Supplier> builder)
    {
        builder.ToTable("Suppliers");
        builder.HasKey(x => x.Id);
        builder.Property(x => x.Name).IsRequired().HasMaxLength(200);
        builder.Property(x => x.Email).IsRequired().HasMaxLength(320);
        builder.Property(x => x.Phone).HasMaxLength(20);
        builder.Property(x => x.CreatedAt).IsRequired();
        builder.HasIndex(x => x.Email).IsUnique();
    }
}

🔁 Zero wiring needed. WriteDbContext calls modelBuilder.ApplyConfigurationsFromAssembly(...) — it discovers SupplierConfiguration automatically.

CreateSupplierEndpoint.cs

Thin Minimal API registration. No business logic — delegates immediately to MediatR.

public static class CreateSupplierEndpoint
{
    public static IEndpointRouteBuilder MapCreateSupplier(
        this IEndpointRouteBuilder app)
    {
        app.MapPost("v1/createsupplier",
            async (CreateSupplierCommand command, IMediator mediator) =>
            {
                var result = await mediator.Send(command);
                return result.IsSuccess
                    ? Results.Created($"v1/createsupplier/{result.Value}", result.Value)
                    : Results.BadRequest(result.Error);
            })
           .WithName("CreateSupplier").WithTags("Supplier")
           .Produces<int>(201).ProducesValidationProblem();
        return app;
    }
}

CreateSupplierValidator.cs — Validation Rules

FluentValidation runs via the MediatR pipeline behaviour before the handler is called. Returns 400 ValidationProblem on failure.

public class CreateSupplierValidator
    : AbstractValidator<CreateSupplierCommand>
{
    public CreateSupplierValidator()
    {
        RuleFor(x => x.Name).NotEmpty().MaximumLength(200);
        RuleFor(x => x.Email).NotEmpty().EmailAddress().MaximumLength(320);
        RuleFor(x => x.Phone).MaximumLength(20).When(x => x.Phone is not null);
    }
}
📄

CreateSupplierHandler.cs — Business Logic

Receives the validated command, maps it to a Supplier entity, persists via WriteDbContext, returns the new ID.

public class CreateSupplierHandler
    : IRequestHandler<CreateSupplierCommand, Result<int>>
{
    private readonly WriteDbContext _db;
    public CreateSupplierHandler(WriteDbContext db) => _db = db;
    public async Task<Result<int>> Handle(CreateSupplierCommand cmd, CancellationToken ct)
    {
        var supplier = new Supplier { Name=cmd.Name, Email=cmd.Email, Phone=cmd.Phone, CreatedAt=DateTime.UtcNow };
        _db.Suppliers.Add(supplier);
        await _db.SaveChangesAsync(ct);
        return Result.Success(supplier.Id);
    }
}

Persistence / DbContext

3 purpose-separated EF Core database contexts

📄

ReadDbContext.cs

Used exclusively by query handlers. Change tracking disabled (AsNoTracking()) for maximum read performance. Never used to save changes.

opts.UseQueryTrackingBehavior(QueryTrackingBehavior.NoTracking);
📄

WriteDbContext.cs

Used exclusively by command handlers. Full change tracking enabled so EF Core can detect mutations and generate correct SQL on SaveChangesAsync().

opts.UseSqlServer(connectionString);
📄

BackgroundDbContext.cs

Used by hosted services and background jobs. Registered with a separate lifetime scope. Injected via IServiceScopeFactory inside a BackgroundService.

var db = scope.ServiceProvider.GetRequiredService<BackgroundDbContext>();
